# Выкладка FinServ в Yandex Cloud

Сайт и ассистент YandexGPT работают в Yandex Cloud и закрыты логином и паролем:

```
браузер ──► API Gateway (https://<id>.apigw.yandexcloud.net)
              ├─ /               → функция auth: окно логина браузера, после входа — переход на /web/
              ├─ /{path+}        → закрытый бакет Object Storage (web/, public/data/, tests/fixtures/)
              ├─ /iss/{path+}, /cbr/{path+} → функция iss-proxy → iss.moex.com / www.cbr.ru
              └─ POST /api/assistant → функция assistant → YandexGPT
```

Всё, кроме «/», проверяет авторизатор (та же функция `auth`). Секреты лежат только в Yandex Lockbox
и GitHub Secrets. Дальнейшие обновления сайта выкладывает GitHub Actions (`.github/workflows/deploy-yc.yml`)
при каждом изменении в `main` и после ежедневного сбора данных.

Настройка делается один раз, примерно за 30–40 минут. Есть два пути: скрипт `infra/setup.sh` (быстрее)
или вручную в консоли (шаги 3–7 ниже). Шаги 1, 2, 8–10 нужны в любом случае.

## 1. Аккаунт и платёжный аккаунт

1. Зайдите на <https://console.yandex.cloud> с Яндекс ID.
2. Создайте платёжный аккаунт (Биллинг → Создать). Новым пользователям дают стартовый грант.
   Расходы проекта маленькие: функции, шлюз и бакет в пределах бесплатного уровня при небольшом числе
   посетителей, но платёжный аккаунт обязателен.
3. Создайте облако (если его нет) и в нём каталог, например `invest-analytics`.

## 2. Доступ к YandexGPT

Ассистент вызывает YandexGPT внутри того же облака, ключ модели не нужен: функция берёт IAM-токен
сервисного аккаунта `ia-runtime`. Нужна роль `ai.languageModels.user` у `ia-runtime` на каталог
(скрипт выдаёт её сам; вручную — шаг 3). Идентификатор каталога передаётся функции переменной
`YC_FOLDER_ID` при выкладке (`.github/workflows/deploy-yc.yml`). Использование модели платное по тарифам
Yandex Cloud (расход — в биллинге).

## 3–7. Быстрый путь: скрипт

1. Установите Yandex Cloud CLI: <https://yandex.cloud/ru/docs/cli/quickstart> и выполните `yc init`
   (выберите облако и каталог из шага 1).
2. Из корня репозитория:
   ```bash
   YC_BUCKET=invest-analytics-<ваша-фамилия> bash infra/setup.sh
   ```
   Скрипт создаст два сервисных аккаунта с ролями (шаг 3), закрытый бакет, секрет Lockbox, API Gateway и
   (по вашему согласию) файл ключа `~/.yc-invest-analytics/sa-key.json` — вне репозитория, чтобы его нельзя
   было случайно закоммитить. Логин и пароль он спросит со скрытым вводом (или возьмёт из
   переменных окружения `SITE_USERS`). Повторный запуск ничего не ломает:
   существующее остаётся. В конце скрипт печатает значения для GitHub — переходите к шагу 8.

   Секрет скрипт передаёт в `yc` через временный файл (права 600), а не аргументом. Что `yc` принимает
   секрет так (`--payload -`), не проверено на живом облаке (уверенность средняя). Если откажет, скрипт
   остановится и попросит создать секрет вручную (шаг 6). После этого запустите скрипт ещё раз —
   он найдёт секрет и продолжит.

## 3–7. Ручной путь: консоль

### 3. Сервисные аккаунты и роли

Два аккаунта: от одного GitHub выкладывает сайт, от другого работают функции и шлюз. Тогда утёкший
ключ из GitHub не даёт прочитать пароли напрямую. Роли выдаются **на конкретный ресурс**,
где это возможно (в консоли: ресурс → «Права доступа» → «Назначить роли»):

| Аккаунт | Роль | На что | Зачем |
|---|---|---|---|
| `ia-deploy` | `functions.editor` | каталог | создание функций и версий (функции создаёт выкладка, поэтому ресурса заранее нет) |
| `ia-deploy` | `api-gateway.editor` | шлюз | обновление спецификации шлюза |
| `ia-deploy` | `iam.serviceAccounts.user` | аккаунт `ia-runtime` | привязать `ia-runtime` к версиям функций и к шлюзу |
| `ia-deploy` | `iam.serviceAccounts.accessKeyAdmin` | аккаунт `ia-deploy` (сам себе) | временный статический ключ для загрузки статики (выкладка сразу его удаляет) |
| `ia-deploy` | полный доступ (ACL) или `storage.editor` | бакет | загрузка статики |
| `ia-deploy` | `lockbox.payloadViewer` | секрет | см. ниже |
| `ia-runtime` | `lockbox.payloadViewer` | секрет | функции читают пользователей |
| `ia-runtime` | `functions.functionInvoker` | каталог | шлюз вызывает функции |
| `ia-runtime` | `ai.languageModels.user` | каталог | ассистент вызывает YandexGPT |
| `ia-runtime` | чтение (ACL) или `storage.viewer` | бакет | шлюз отдаёт статику |

Почему у `ia-deploy` есть `lockbox.payloadViewer`: точно не известно, требует ли Yandex Cloud эту роль
у того, кто создаёт версию функции с привязкой секрета (`--secret`). Роль выдана только на один секрет,
не на каталог. При желании её можно снять. Если после этого выкладка упадёт на шаге «Cloud Functions»
с `PermissionDenied`, роль нужно вернуть.

Доступ к бакету скрипт задаёт через ACL бакета («Права доступа» в настройках бакета). Если ACL задать
не получилось, он выдаёт `storage.editor`/`storage.viewer` на каталог: в отдельном каталоге проекта
это почти то же самое. Роль `serverless.functions.admin` не нужна.

`YC_SA_ID` в GitHub — это идентификатор **`ia-runtime`**, ключ для GitHub — от **`ia-deploy`**.

Упрощённый вариант: один аккаунт со всеми ролями выше. Работает, но утёкший ключ даёт полный доступ.

### 4. Бакет

Object Storage → «Создать бакет»: имя уникальное (например `invest-analytics-ivanov`), **доступ на чтение
объектов, к списку объектов и настройкам — «Ограниченный»** (бакет закрытый, сайт отдаёт шлюз),
класс хранилища «Стандартное», максимальный размер 1 ГБ.

### 5. Строка пользователей `SITE_USERS`

Пароль — **случайный, не короче 16 символов**: сгенерируйте его в менеджере паролей. Окно логина
доступно всем в интернете, поэтому короткий пароль подбирается.

Формат: `логин:соль:хэш`, где хэш — PBKDF2-HMAC-SHA256 (200 000 итераций) от пароля со случайной солью.
Несколько пользователей — через запятую. Сгенерировать строку (пароль вводится скрыто и не попадает
в историю команд):

```bash
python3 -c "import getpass,hashlib,os;l=input('Логин: ');p=getpass.getpass('Пароль: ');assert len(p)>=16,'пароль короче 16 символов';s=os.urandom(16);print(l+':'+s.hex()+':'+hashlib.pbkdf2_hmac('sha256',p.encode(),s,200000).hex())"
```

Результат выглядит как `ivan:<соль>:<хэш>`. Для двух человек: `ivan:<соль>:<хэш>,maria:<соль>:<хэш>`.
В логине не используйте `:` и `,`. Сама строка не секретна так, как пароль, но держите её только в Lockbox.

### 6. Секрет Lockbox

Lockbox → «Создать секрет», имя `invest-analytics`, одна пара «ключ — значение»:

| Ключ | Значение |
|---|---|
| `SITE_USERS` | строка из шага 5 |

Это и основной путь, если скрипт не смог передать секрет. Сменить пароль — «Добавить версию»
в секрете, затем перезапустить выкладку (шаг 9).

### 7. API Gateway

API Gateway → «Создать API-шлюз», имя `invest-analytics`, в спецификации оставьте пример по умолчанию
(настоящую `infra/gateway.yaml` поставит выкладка). Скопируйте **идентификатор** шлюза и его домен.

Функции `assistant` и `auth` создавать не нужно — выкладка создаст их сама.

## 8. Ключ сервисного аккаунта и настройки GitHub

1. Аккаунт `ia-deploy` → «Создать новый ключ» → **«Создать авторизованный ключ»** → скачать JSON.
   Скрипт делает это сам и кладёт файл в `~/.yc-invest-analytics/sa-key.json`. **Не храните ключ
   в папке репозитория.** `.gitignore` страхует от `yc-sa-key.json` и `*.sa-key.json`, но не от любых имён.
2. В репозитории GitHub: Settings → Secrets and variables → Actions.

   **Secrets** (вкладка Secrets → New repository secret):

   | Имя | Значение |
   |---|---|
   | `YC_SA_JSON_CREDENTIALS` | всё содержимое JSON-файла ключа `ia-deploy` |
   | `YC_CLOUD_ID` | идентификатор облака |
   | `YC_FOLDER_ID` | идентификатор каталога |

   **Variables** (вкладка Variables → New repository variable):

   | Имя | Значение |
   |---|---|
   | `YC_BUCKET` | имя бакета |
   | `YC_GATEWAY_ID` | идентификатор API-шлюза |
   | `YC_SA_ID` | идентификатор аккаунта `ia-runtime` |
   | `YC_LOCKBOX_SECRET_ID` | идентификатор секрета Lockbox |

3. **Удалите JSON-файл ключа с компьютера** (`rm ~/.yc-invest-analytics/sa-key.json`). Если он утёк —
   удалите ключ в консоли (аккаунт `ia-deploy` → ключи) и выпустите новый.

## 9. Первая выкладка

GitHub → Actions → «Выкладка в Yandex Cloud» → Run workflow. Через 2–3 минуты откройте
`https://<домен шлюза>/` — **именно корень**: браузер спросит логин и пароль, затем откроется сайт.
Прямая ссылка на `/web/` без входа даст ошибку доступа без окна логина (так устроен шлюз) — тогда
откройте корень. Выйти — закрыть браузер (или окно инкогнито).

Пока секретов в GitHub нет, выкладка завершается с предупреждением и ничего не делает.

## 10. Бюджет-уведомление

Биллинг → ваш платёжный аккаунт → «Бюджеты» → «Создать бюджет»: тип «Расходы», сумма например 300 ₽
в месяц, область — облако проекта, пороги уведомлений 50 %, 80 %, 100 % на вашу почту.
Бюджет только предупреждает и не останавливает ресурсы. Расход YandexGPT (токены) входит в счёт облака.

## Что где настраивается

| Что | Где |
|---|---|
| Лимит вопросов в минуту на IP (по умолчанию 10), модель (`yandexgpt`; `yandexgpt-lite` дешевле и быстрее) | переменные `RATE_LIMIT_PER_MIN`, `YANDEX_MODEL` функции `assistant` — задавать флагом `--environment` в `.github/workflows/deploy-yc.yml` (правка в консоли пропадёт при следующей выкладке) |
| Время кэширования проверки пароля шлюзом | `authorizer_result_ttl_in_seconds` в `infra/gateway.yaml` |
| Журналы функций | Cloud Functions → функция → «Логи» (там только маршрут, длины, коды и время) |

## Если что-то не работает

* **Окно логина не появляется, сразу ошибка 401/403** — откройте корень сайта `/`, а не `/web/`.
* **Логин не подходит** — проверьте `SITE_USERS` в Lockbox: формат `логин:соль:хэш`, без пробелов, и перезапустите
  выкладку. Смена пароля вступает в силу до 5 минут (кэш авторизатора).
* **Ассистент отвечает «YandexGPT не отвечает» / «Нет доступа» / «Лимит запросов»** — в логах функции `assistant`
  поле `upstream`: `auth: …` — нет IAM-токена (у функции не привязан `ia-runtime`) или не задан `YC_FOLDER_ID`;
  `chat: 403` — нет роли `ai.languageModels.user` у `ia-runtime`; `chat: 429` — лимит запросов;
  `chat: ReadTimeout` — модель не ответила за 25 с.
* **Ошибка «permission denied» в выкладке** — у сервисного аккаунта не хватает роли из шага 3.

## Если вы раньше использовали GigaChat

Секрет Lockbox теперь содержит только `SITE_USERS`. Ключ `GIGACHAT_AUTH_KEY` в уже созданном секрете остаётся
неиспользованным — его можно удалить в консоли (новой версией секрета без этого ключа).

## Прокси биржи и ЦБ (функция `iss-proxy`)

`iss.moex.com` отдаёт сертификат УЦ Минцифры, которому браузеры без корневого сертификата не доверяют.
Поэтому на домене шлюза есть `/iss/...` и `/cbr/...`: функция `functions/iss-proxy` сама ходит на биржу
(сертификаты — `functions/iss-proxy/russian_trusted_ca.pem`) и на сайт ЦБ. Только GET, пути из белого списка,
без секретов; создаётся и обновляется тем же `deploy-yc.yml`, отдельной настройки не нужно.
Проверка после выкладки: откройте `https://<домен шлюза>/iss/index.json?iss.meta=off` (после логина) —
должен прийти JSON; `/cbr/scripts/XML_daily.asp?date_req=01/12/2025` — XML с курсами.
